# Архитектура «Вехи»: ландшафт, контуры, управление расхождениями

**Дата:** 2026-09-05
**Статус:** проектный документ — направление, а не описание сделанного. Что реализовано и
чего нет — [docs/wiki/status.md](wiki/status.md).
**Имена:** проект — «Веха»; `atlas` ниже — техническое имя данных (`atlas.yaml`, каталог
`atlas/`) и агента `partest-atlas`. Соглашение — в [README](../README.md).

Документ описывает, как из инструмента для одного проекта получается инструмент, который
выдерживает ландшафт из многих систем и работает там, где документацию **не готовы
немедленно привести в порядок**.

---

## 1. Отправная точка: что было и что этому мешает

| Что есть в однопроектной версии | Что ломается на ландшафте из многих систем |
|---|---|
| Один корень проекта, поиск `atlas.yaml` вверх по дереву | Ландшафт — это 5–15 систем, у каждой свой конфиг |
| Один `artifacts_dir`, плоские имена файлов | Артефакты разных систем и контуров перезапишут друг друга |
| Версия схемы артефактов без области действия | В файле не написано, к какой системе и контуру он относится |
| Один глобальный кеш графа | Переключение контура пересобирает всё |
| Модель ~4 МБ на ~270 узлов, ~10 мс на кадр на ~290 узлах | 12 систем × 250 узлов = 3 000 узлов и ~40 МБ |
| Расхождения считаются, но не имеют состояния | Десятки находок в первый день = инструмент выключают на второй |

Строки 2 и 3 к 2026-10 закрыты: схема артефактов 2 с областью и раскладка
`atlas/<система>/<контур>/` есть у агента и у сервера.

Последняя строка — главная. Технически всё остальное решаемо; а вот инструмент, который на
старте выдаёт команде сотню красных находок и не даёт с ними ничего сделать, кроме как
«всё исправить», не доживает до второго месяца.

---

## 2. Три оси, которые нельзя называть одним словом

Сейчас слово «слой» означает колонку карты (палубу «Объёма»). Добавляются ещё две сущности, и путать их нельзя.

| Ось | Что это | Значения | Кто задаёт |
|---|---|---|---|
| **Палуба** (существует) | горизонт архитектуры внутри одной системы | frontend · api · шина и сервисы · хранилища | код карты |
| **Система** (новое) | самостоятельный продукт в ландшафте | интернет-магазин · мобильный бэкенд · портал · 1С:УТ · WMS · кассы | `atlas.yaml` |
| **Контур** (новое) | среда, в которой эта система развёрнута | dev · test · preprod · прод-подобный | `atlas.yaml` |

Из этого вытекает вся остальная спецификация: артефакт принадлежит паре
**(система, контур)**, узел живёт на палубе внутри системы, а связь может быть либо
внутрисистемной, либо межсистемной интеграцией.

## 3. Модель данных

### 3.1 Сущности

```text
Landscape                       один экземпляр Вехи = один ландшафт
├── System        key, label, owner, config
│   ├── Environment  key, label, урлы/креды через env-переменные, freshness
│   └── Node         id, layer, kind, system, meta
├── Edge          from, to, kind, evidence, via, system|cross
├── Integration   межсистемная связь: from_system, to_system, via, evidence
├── Finding       расхождение: id, kind, key, scope, evidence, first_seen, status
└── Decision      решение человека по находке или по селектору
```

### 3.2 Ключевые поля

**`scope`** — обязателен везде, где раньше подразумевался «текущий проект»:

```json
{"system": "shop", "env": "test"}
```

**`evidence`** — общее для всех связей и находок, обязательно на каждой (красная линия 7 в
[README](../README.md)): `measured` (снято на прогоне) · `inferred` (выведено эвристикой,
названной честно) · `declared` (человек сказал: ручная карта, маркер требования).

**`freshness`** — когда снят источник. Для одного контура это удобство, для сравнения
контуров — условие корректности: сравнивать схему, снятую сегодня, со снятой три недели
назад, нельзя, и инструмент обязан об этом сказать, а не молча показать «разъехалось».

### 3.3 Версия схемы артефактов

`SCHEMA_VERSION` → **2**. Заголовок артефакта:

```json
{
  "version": 2,
  "kind": "db.schema",
  "scope": {"system": "shop", "env": "test"},
  "collected_at": "2026-09-05T11:20:31+03:00",
  "collector": "partest_atlas.collect.db_schema/1.4.0",
  "tables": [...]
}
```

Замысел был читать артефакт версии 1 как «система по умолчанию, контур по умолчанию».
Реализация пошла иначе: сервер читает только схему 2, а файлы схемы 1 перечисляет как
непрочитанные; перенос истории прогонов — открытый вопрос в
[proposals](wiki/proposals.md) («обёртка v1 → v2»).

## 4. Многосистемность и многоконтурность

### 4.1 Конфигурация

`atlas.yaml` в корне становится **манифестом ландшафта**, а сегодняшний его формат целиком
переезжает в файл системы. Это важно: ничего из написанного не выбрасывается.

```yaml
# atlas.yaml — манифест ландшафта
landscape:
  name: "Розничная сеть N"

systems:
  shop:    {label: "Интернет-магазин", include: systems/shop.yaml}
  mobile:  {label: "Мобильный бэкенд",  include: systems/mobile.yaml}
  erp1c:   {label: "1С:Управление торговлей", include: systems/erp1c.yaml}
  wms:     {label: "WMS склада",        include: systems/wms.yaml}

environments:
  test:    {label: "Тест", default: true}
  preprod: {label: "Препрод"}

# Межсистемные интеграции — верхний уровень карты.
# Начинаются как declared, замещаются measured по мере появления источников.
integrations:
  - from: shop.api
    to: erp1c.odata
    via: rabbitmq:orders.created
    evidence: declared
    note: "Заказ уходит в учётную систему; подтверждается адаптером RabbitMQ"
```

`systems/shop.yaml` — сегодняшний `atlas.yaml` без изменений, плюс переопределения по контурам:

```yaml
project: {name: "Интернет-магазин", api_prefix: /api/v1}
containers: {...}      # как сейчас
domains: {...}
database: {...}

environments:
  test:
    database:  {url_env: SHOP_DB_URL_TEST}
    openapi:   {url_env: SHOP_OPENAPI_TEST}
  preprod:
    database:  {url_env: SHOP_DB_URL_PREPROD}
    openapi:   {url_env: SHOP_OPENAPI_PREPROD}
    collect:   {db_effects: false, bus_flow: false}   # на препроде только чтение схемы
```

Последняя строка — не мелочь. На препроде замер `db_effects` недопустим: он держит выдержку
и попадает в чужую активность. Возможность **выключить сборщик на конкретном контуре**
обязана быть в конфиге, иначе инструмент нельзя подключить к препроду вовсе.

### 4.2 Раскладка артефактов

```text
atlas/
  index.json                       реестр: системы, контуры, время сбора, размеры, хеши
  shop/test/db_schema.json
  shop/test/ui_flow.json
  shop/preprod/db_schema.json
  erp1c/test/odata.json
  cache/shop/test/graph.json       собранный граф, восстановимый
  governance/findings.json         текущие находки (производное)
  decisions.yaml                   решения людей — в репозитории, под ревью
```

Правило: **всё в `atlas/` восстановимо пересбором, кроме `decisions.yaml`.** Это единственный
файл, который нельзя потерять, и единственный, который должен проходить ревью в merge request
команды — потому что в нём написано, что команда решила считать нормой.

### 4.3 Сборка графа

Три уровня, и каждый строится отдельно:

| Уровень | Что в узлах | Когда строится |
|---|---|---|
| **Ландшафт** | системы и межсистемные интеграции; на узле — агрегат (покрытие, свежесть, число открытых находок) | по `index.json`, без чтения всех артефактов |
| **Система** | сегодняшняя сцена: экраны, эндпоинты, топики, таблицы | по запросу, кешируется на `(system, env)` |
| **Узел** | карточка: тесты, шаги, обмен, требования, находки | по запросу, как сейчас |

Кеш становится словарём `_cache[(system, env)]` вместо одного значения, с вытеснением по
LRU и лимитом — иначе двенадцать систем × два контура удержат в памяти полгигабайта.

### 4.4 API

```text
GET  /api/landscape                                карта верхнего уровня
GET  /api/graph?system=shop&env=test               сцена системы (как сейчас)
GET  /api/node/{id}?system=shop&env=test
GET  /api/diff?system=shop&from=test&to=preprod    сравнение контуров
GET  /api/findings?system=&env=&kind=&status=
POST /api/decisions                                принять / исключить из оценки
POST /api/baseline                                 зафиксировать эталон
GET  /api/freshness                                когда что снималось
```

### 4.5 Интерфейс

Два новых переключателя в шапке: **система** и **контур**. Оба глобальные, оба в постоянной
ссылке (`?system=shop&env=preprod&node=...`; постоянные ссылки — в плане).

Обязательный элемент рядом с переключателем контура: **дата сбора**. «Препрод, данные от
24.08 — 12 дней» приглушённым текстом. Без этого сравнение контуров превращается в
генератор ложных расхождений.

### 4.6 Где отрисовывается вебморда

Вебморда — часть сервера «Веха», и другого места у неё быть не может: она показывает то,
что знает только сервер — сведённый граф, находки, эталон. Агент к интерфейсу отношения не
имеет вовсе: он пишет файлы и молчит.

| Слой | Где исполняется | Чем является |
|---|---|---|
| Сборка модели | процесс сервера | Python: граф, находки, governance |
| Раздача | тот же процесс, FastAPI | JSON по `/api/*` и статика по `/` |
| Отрисовка | браузер пользователя | карта по слоям — SVG, объёмный вид — Canvas 2D; раскладка и проекция считаются вручную |

Три свойства, которые сохраняем намеренно, — каждое отвечает на требование работы без
интернета и без лишней инфраструктуры:

1. **Ни WebGL, ни сборки, ни npm.** Статика отдаётся тем же приложением, что и API.
   Ставится без Node вообще: устанавливать нечего, кроме пакета Python.
2. **Ни одного внешнего запроса из браузера.** Ни CDN, ни шрифтов, ни аналитики. Вебморда
   обязана открываться на машине без интернета — это проверяется тестами.
3. **Один процесс, один порт.** Отдельного фронтового сервиса нет: второй контейнер удвоил бы
   то, что надо развернуть и обновить, и не дал бы ничего.

Оформление — в языке сайта partest.ru: светлая и тёмная тема по настройке системы, системные
шрифты, один зелёный акцент. Цвет несёт только покрытие и прогон; связи видны у выбранного
узла, их происхождение — начертанием линии. Почему так — [решение](wiki/decisions/visual-language.md).

**Чего пока нет и что обязательно до установки, к которой ходит больше одного
человека, — аутентификация.** Сейчас приложение поднимается на `localhost`, а на
карточках узлов видны фрагменты запросов и ответов. Минимум:

- вход через OIDC организации (Keycloak и подобные) с фолбэком на локальные учётные записи;
- две роли — **чтение** и **решения**: принимать находки и заводить waiver может не всякий,
  потому что `decisions.yaml` — это утверждение о том, что команда считает нормой;
- запуск наборов из вебморды — отдельное право, иначе кнопка «Прогнать всё» доступна любому
  зашедшему;
- всё, что уходит в интерфейс, проходит через `partest.redact`.

Без этого сервер нельзя открывать дальше loopback: доступ к карте — это доступ к
описанию всей системы.

## 5. Сравнение контуров

Отдельный режим, и для ландшафта из нескольких контуров он может оказаться ценнее самой
карты: «что разъехалось между тестом и препродом» — ежедневный вопрос, который сегодня
выясняют вручную.

| Вид расхождения | `kind` | Источник |
|---|---|---|
| Таблица/колонка есть в одном контуре и нет в другом | `env.schema.missing` | `db.schema` обоих контуров |
| Тип или nullability колонки различаются | `env.schema.type` | то же |
| Эндпоинт объявлен в одном контракте и отсутствует в другом | `env.contract.missing` | `contract.openapi` |
| Контейнер другой версии / другого образа | `env.container.version` | адаптер контейнеров |
| Топик есть на одном брокере и нет на другом | `env.bus.missing` | `bus.flow --probe` |

Три правила, без которых режим врёт:

1. **Сравнивать только снимки сопоставимой свежести.** Разница больше порога
   (`diff.max_age_skew`, по умолчанию 48 часов) — предупреждение поверх результата.
2. **Направление имеет смысл.** «Есть в тесте, нет на препроде» — обычно грядущий релиз,
   а не дефект. Обратное — почти всегда дефект. Показывать раздельно.
3. **Не сравнивать данные.** Только структуру. Строки таблиц наружу не выходят никогда —
   это же и есть ответ службе безопасности.

## 6. Управление расхождениями: эталон, принятие, исключение

Ядро ответа на «команда не готова приводить всё в актуальное состояние».

### 6.1 Находка (`Finding`)

Всё, что Веха умеет обнаруживать, приводится к одному типу записи. Сегодня это считается
и показывается, но не имеет ни идентичности, ни состояния.

| `kind` | Что значит | Уже считается |
|---|---|---|
| `contract.undeclared` | вызывается, но не объявлено в контракте | да |
| `contract.unused` | объявлено, но за прогон не вызывалось | да |
| `contract.codes` | контракт не объявляет ошибочных кодов | да, как системный факт |
| `spec.path_missing` | спецификация описывает путь, которого нет | да |
| `spec.untested` | требование без единого теста | да |
| `map.drift` | ручная разметка `app_map.yaml` расходится со снятым | частично (сверка логов) |
| `db.untouched` | таблица, которую не трогает ни один тест | нет |
| `ui.uncovered` | элемент экрана без покрытия | нет (ждёт методики покрытия фронта) |
| `hold.surface` | поверхность, которую тесты не смогли наблюдать | нет — берётся из `partest.sideeffects.held_surfaces()` |
| `env.*` | расхождение между контурами | нет, см. §5 |
| `load.*` | деградация под нагрузкой, точка насыщения, общее узкое место | нет — берётся из `partest-load`, см. §6.8 |

### 6.2 Стабильный идентификатор — техническая сердцевина

Если id находки пляшет между пересборами, эталон рассыпается на второй день.

```
finding_id = sha1(f"{kind}|{system}|{key}")[:12]
```

где `key` — **канонический ключ объекта**, и правило одно: в него не входит ничего, что
меняется от прогона к прогону.

| `kind` | `key` |
|---|---|
| `contract.undeclared` | `DELETE /api/v1/carts/{id}/items/{itemId}` — шаблон, не конкретный URL |
| `spec.path_missing` | `REQ-10.4\|/stock-transfers/{id}` |
| `db.untouched` | `public.stock_transfer` |
| `map.drift` | `screen:orders_list\|control:orders-create-btn` |
| `env.schema.type` | `test→preprod\|public.order_header.status` |

**Не входят:** номера строк, даты, счётчики вызовов, порядковые номера, конкретные id
сущностей. Шаблонизация путей берётся из `partest.path_match` — той же, что считает
покрытие, иначе ключи разъедутся между отчётом и картой.

Контур в ключ **не входит намеренно**: одна и та же находка на тесте и препроде — одна
находка, у которой два наблюдения. Иначе принятие придётся повторять на каждом контуре.

### 6.3 Четыре состояния

| Статус | Смысл | В метриках | На карте |
|---|---|---|---|
| `open` | новое, не разобранное | ухудшает | ярко, в счётчике |
| `accepted` | «да, так и есть; менять не будем сейчас» | не ухудшает, считается отдельной строкой | приглушённо, с датой и причиной |
| `waived` | сознательно вне оценки | исключено из знаменателя | серым, в отдельном списке |
| `resolved` | исчезло при пересборе | не считается | в истории |

Переходы `open → accepted|waived` делает **человек**, `→ resolved` и `resolved → open`
(вернулось) — инструмент.

### 6.4 Решения — файл, который ревьюят

`atlas/decisions.yaml` лежит в репозитории тестов. Это не настройка инструмента, это
утверждение команды о том, что считать нормой, и оно должно проходить через merge
request, как код.

```yaml
decisions:
  - id: 7f3a91c2b840
    kind: contract.undeclared
    key: "DELETE /api/v1/carts/{id}/items/{itemId}"
    status: accepted
    reason: "Удаление строки корзины намеренно не публикуется в контракте"
    ticket: SHOP-142
    by: dev-1
    at: 2026-09-05
    until: 2027-03-05

  - status: waived
    match: {kind: "*", path: "/api/v1/internal/*"}
    scope: {system: shop, env: "*"}
    reason: "Внутренний контур платформенной команды, покрывается ими"
    by: dev-1
    at: 2026-09-05
    until: 2027-09-05
```

### 6.5 Четыре правила, без которых механизм превращается в свалку

Это то место, где такие инструменты обычно и умирают: команда один раз массово «принимает»
всё и больше никогда не смотрит.

1. **Принятие не делает находку невидимой.** Она уходит из красного, но остаётся в списке
   с датой, автором и причиной. Отдельный счётчик «принято» виден рядом с «открыто» всегда.
2. **У каждого решения есть срок.** `until` обязателен, по умолчанию 180 дней. По истечении
   находка возвращается в `open` — не как наказание, а потому что «пока не чиним» через
   полгода перестаёт быть правдой. Продлить — одно действие и новая запись в истории.
3. **Широкий waiver отчитывается о своём аппетите.** Селектор по маске покрывает и будущие
   объекты; Веха показывает рядом с ним «накрыл 14 новых объектов с момента создания».
   Иначе один `/internal/*` тихо съест половину новой функциональности.
4. **Знаменатель всегда на экране.** Покрытие 100% при трети системы в waiver — это не 100%.
   Метрика показывается парой: **«92% от оцениваемого · вне оценки 31% системы»**.
   Одно число без второго запрещено на уровне модели, а не соглашения.

### 6.6 Эталон

```bash
veha baseline create --system shop --env test --reason "Стартовое состояние на начало внедрения"
```

Все текущие `open` переводятся в `accepted` одной записью со ссылкой на эталон и общим
сроком. С этого момента главная метрика — не «сколько всего расхождений», а
**дельта к эталону**:

```
Δ с 2026-09-05:  +7 новых · −12 исчезло · 3 принятия просрочены
```

Это и есть рычаг для команды, которая не готова чинить историю: она фиксирует прошлое как
данность и отвечает только за то, что добавила сама. Ровно так работают baseline у
линтеров, и именно поэтому их внедряют в легаси, а не только в новых проектах.

```bash
veha baseline diff --fail-on new --max-new 0     # в CI
```

Эта команда — то, ради чего механизм вообще нужен: она встраивается в пайплайн и начинает
защищать эталон каждый день, а не раз в квартал.

### 6.7 Режим наблюдения для новых источников

Новый сборщик или новый адаптер подключается в режиме `observe`: находки собираются,
показываются, **но не влияют на метрики** заданное число дней (по умолчанию 14).

Причина простая и проверенная на практике: первый запуск `container_logs` без
`known_only` тащил в находки каждое имя класса из журналов. Если бы это сразу испортило
цифры, источник отключили бы, не разобравшись. Режим наблюдения — способ дать источнику
время настроиться, не потеряв доверие к инструменту.

### 6.8 Нагрузка как источник находок

`partest-load` даёт артефакт `load.profile` на каждый эндпоинт: достигнутый RPS, перцентили
задержки, доля ошибок, точка насыщения, наклон деградации. Сам по себе это ещё один отчёт —
таких инструментов много. Ценность появляется при наложении на граф, и она из тех, которую
нельзя получить нигде больше:

| `kind` | Что значит | Откуда |
|---|---|---|
| `load.degradation` | p95 эндпоинта хуже эталона более чем на порог | `load.profile` + эталон |
| `load.saturation` | точка насыщения ниже заявленной нагрузки | `load.profile` |
| `load.shared_bottleneck` | **несколько эндпоинтов деградируют одновременно, и все ведут в одну таблицу, топик или контейнер** | `load.profile` × рёбра графа |
| `load.uncovered_hot` | узел с высокой нагрузкой и нулевым покрытием | `load.profile` × `coverage` |

Третья строка — то, ради чего связка вообще нужна. Нагрузочный инструмент в одиночку
говорит «эндпоинт X деградирует на 200 RPS». Веха говорит: «X, Y и Z деградируют вместе,
и за всеми тремя стоит таблица `stock_reserve`, в которую пишет ещё и консьюмер шины». Это
не отчёт о симптоме, а указание на причину, и получается оно из уже имеющихся рёбер — новой
эвристики не требуется.

Четвёртая строка закрывает старый спор о приоритетах покрытия объективным числом: эндпоинт,
который держит основную нагрузку и не покрыт ничем, важнее десяти редких.

**Эталон производительности — тот же механизм, что и для расхождений.** `p95` фиксируется
на дату, дальше считается дельта, отклонение принимается через `decisions.yaml` с причиной
и сроком, `veha baseline diff --fail-on new` ловит регрессию в CI. Ничего отдельного
строить не нужно: производительность становится ещё одним видом находки со своим
`evidence: measured`.

## 7. Хранение: что в файлах, что в базе

| Данные | Где | Почему |
|---|---|---|
| Артефакты сбора | JSON-файлы, как сейчас | дописываются параллельными воркерами, переносятся копированием, читаются глазами |
| Решения (`decisions.yaml`) | файл в репозитории тестов | должен проходить ревью |
| Находки, история, кеш графов, индекс свежести | **SQLite** в `atlas/atlas.db` | нужны запросы, диффы и история за год; JSON на этом задыхается |

Правило, которое надо соблюсти: **`atlas.db` восстановим полностью** из артефактов и
`decisions.yaml`. Удалили — пересобрали. Бэкап базы не нужен, и это свойство стоит больше,
чем производительность.

Внешней СУБД у Вехи нет и не должно быть: отдельный PostgreSQL ради инструмента — ещё
один сервис в эксплуатации и ноль ценности.

## 8. Производительность и пределы

| Показатель | Сейчас | Ландшафт из многих систем | Что делаем |
|---|---|---|---|
| Узлов в сцене | ~300 | до ~400 на систему | без изменений |
| Узлов в ландшафте | — | 5–15 | тривиально |
| Кадр | ~10 мс при ~290 узлах | так же — рисуем одну систему | без изменений |
| Модель в памяти | ~4 МБ | ×24 при жадной загрузке | ленивая загрузка + LRU-кеш на 3 системы |
| Первая загрузка | приемлемо | зависит от числа артефактов | `index.json` без чтения тел |

Ключевое проектное решение: **ландшафт никогда не рисуется как одна большая сцена.** Пять
тысяч узлов не читаются человеком ни при каком рендерере, и уход в WebGL этой задачи не
решает — он решает другую. WebGL остаётся в бэклоге на случай одной очень большой системы
(1000+ узлов), а не на случай большого ландшафта.

## 9. Подключение к тестам

Вопрос «куда ставится обвязка» имеет один ответ, и он не про репозитории.

### 9.1 Три класса сборщиков

Разделение проходит по тому, нужен ли доступ **внутрь процесса**, где выполняются тесты.

| Класс | Кто | Где обязан находиться |
|---|---|---|
| **Внутрипроцессные** | `pytest_ui_flow`, `pytest_db_effects`, `pytest_bus_flow`, маркер `req` | только в процессе прогона тестов |
| **Внепроцессные** | `db_schema`, `openapi`, `container_logs`, `specs`, зонд шины | где угодно при наличии доступов — например, рядом с сервером |
| **Чтение постфактум** | `allure-results`, `junit.xml`, `coverage.json` | без внедрения вообще, читаются как файлы |

### 9.2 Топология

```text
[Репозиторий тестов]                      [Сервер Веха]
  pip install partest-atlas                 вебморда, governance
  pytest11 entry point,                     внепроцессные сборщики
  молчит без переменных окружения           сборка графа, находки
            │ пишет                                ▲ читает
            └──────► atlas/<system>/<env>/*.json ──┘
                     allure-results/
```

**Единственная точка стыка — каталог артефактов.** Из этого следуют два правила, которые
нельзя нарушать: Веха не живёт в репозитории тестов и не форкает их; тесты не зависят от
Вехи в рантайме — выключенный агент не должен стоить прогону ничего, включая время
импорта.

### 9.3 Три уровня внедрения в прогон

Подключать снизу вверх: первый уровень не требует от команды ни строки в коде, и поэтому
его проще всего согласовать.

| Уровень | Что делает команда | Что даёт | Точность |
|---|---|---|---|
| **1 · Обёртка** `partest-atlas wrap -- <их команда>` | ничего в коде | схема, смещения топиков, `pg_stat` до и после прогона | режим `session` — «что задел прогон» |
| **2 · Агент** — одна зависимость | ставит пакет, выставляет `ATLAS_*` | + `ui_flow`, `db_effects`, `bus_flow` вокруг каждого теста | режим `test` — «какой тест задел» |
| **3 · Маркеры** | правит тесты | + трассируемость требований (`evidence: declared`), точный отбор под замер | максимум |

Обёртка работает с любым раннером — Newman, k6, Vanessa Automation, запуск из 1С, — потому
что снимает состояние снаружи процесса. Отсюда граница возможностей: структура и «что
задел прогон» достижимы на любом стеке, «какой тест задел» требует агента, а агент
существует только для pytest. Для другого раннера это означает написание адаптера.

### 9.4 Как артефакты попадают в Веху

| Способ | Когда | Чем платим |
|---|---|---|
| Общий том | сервер и раннер тестов на одной машине или в одном кластере | ничем, вариант по умолчанию |
| Забор из CI | тесты идут в GitLab/Jenkins, артефакты job'а | адаптер `ci/*`, токен на чтение |
| Загрузка через вебморду (`POST /api/artifacts`) | сеть без доступа к CI, 1С, ручной прогон | руками, но работает всегда |

**Раннер Вехи — удобство, а не путь поставки данных.** Сегодня `runner.py` запускает pytest
сам, и при локальной работе это основной сценарий. Обычно же тесты гоняет CI, и Веха
обязана уметь просто подобрать результат. Порядок приоритетов при внедрении именно такой.

### 9.5 Три стартовых состояния проекта

| | Что есть | Что делаем | До первой карты |
|---|---|---|---|
| **A** | pytest + Allure | агент, переменные, монтирование каталога | часы |
| **B** | тесты есть, но не pytest | обёртка + внепроцессные сборщики + адаптер отчётов | 1–3 дня |
| **C** | тестов нет | зонд + внепроцессные сборщики | 1–2 дня |

### 9.6 Проект без тестов: порядок обратный

Не «сначала пишем тесты, потом подключаем карту».

1. Карта по зонду и внепроцессным источникам — полная по структуре, **полностью серая по
   покрытию**.
2. Серая карта — материал для планирования: команда впервые видит свою систему целиком и
   то, что не проверено ничего.
3. Тесты пишутся **по карте**: приоритет по числу связей узла, по критичности таблиц, по
   требованиям без покрытия. Это partest и методика — отдельный проект.
4. Карта раскрашивается по мере появления тестов; прогресс виден еженедельно.

**Зонд не даёт покрытия.** Он обходит объявленные эндпоинты и смотрит, кто отвечает и что
читается, — то есть достраивает структуру, но ничего не проверяет. Его наблюдения несут
`evidence: measured`, но **не участвуют в расчёте покрытия** и помечены источником `probe`.
Инструмент, засчитавший себе покрытие за собственные обращения, врал бы ровно в том месте,
ради которого его ставят.

### 9.7 Чего не делаем

**Не заводим отдельный набор тестов ради карты.** Соблазн понятен — свои тесты, свой
контейнер, полный контроль над сбором. Три причины, по которым это тупик:

1. Карта покажет покрытие этих тестов, а не тестов команды. Ценность — ответ «что не
   покрыто **у вас**».
2. Два набора тестов дают два разных ответа на один вопрос, и команда перестаёт верить обоим.
3. Появляется второй набор тестов, который тоже надо поддерживать, — и поддерживать его
   некому, кроме авторов карты.

## 10. Этапы реализации

Порядок выбран так, чтобы каждый этап давал самостоятельную ценность, — на случай, если
приоритеты изменятся. Отметки о готовности здесь не ведутся: что сделано —
[status](wiki/status.md).

### Этап A — идентичность и состояние находок (2 недели)

Самый ценный и самый дешёвый. Работает на одной системе, без всякой многоконтурности.

- [ ] Привести существующие расчёты расхождений к типу `Finding` со стабильным `id`.
- [ ] `decisions.yaml`, четыре статуса, срок `until`, история переходов.
- [ ] `veha baseline create` / `diff --fail-on new`.
- [ ] Парная метрика «от оцениваемого · вне оценки» — на уровне модели, не в шаблоне.
- [ ] Отчёт по аппетиту широких waiver.

### Этап B — область действия у артефактов (1 неделя)

- [ ] `SCHEMA_VERSION = 2`, поле `scope`, `collected_at`, `collector`.
- [ ] Раскладка `atlas/<system>/<env>/`, `index.json`.
- [ ] Чтение артефактов версии 1 как «система и контур по умолчанию».

### Этап C — контуры (2 недели)

- [ ] `environments` в конфиге системы, переопределения, выключение сборщиков на контуре.
- [ ] Переключатель контура + индикатор свежести.
- [ ] `/api/diff`, режим сравнения, пять видов `env.*`, правило перекоса свежести.

### Этап D — ландшафт (2–3 недели)

- [ ] Манифест ландшафта, `include` файлов систем.
- [ ] Карта верхнего уровня, `integrations`, drill-down.
- [ ] Кеш на `(system, env)` с LRU, ленивая загрузка.

### Этап E — обёртка и зонд (1–2 недели)

Открывает сценарии B и C из §9.5, то есть все стеки за пределами pytest.

- [ ] `partest-atlas wrap -- <команда>`: снимки до и после произвольного прогона, режим `session`
      без единой строки в коде тестов.
- [ ] Зонд по объявленным эндпоинтам с источником `probe`, исключённым из расчёта покрытия.
- [ ] Приём артефактов через `POST /api/artifacts` для сетей без доступа к CI.

### Этап F — источники под нетиповой стек (по мере надобности)

Адаптеры пишутся под конкретный стек и остаются в проекте. Порядок диктуют настоящие
установки, а не план.

## 11. Что решается только на настоящих установках

Эти вопросы намеренно оставлены открытыми: у них нет правильного ответа, пока нет
нескольких настоящих установок, и придумывать его сейчас — значит закладывать неверную абстракцию.

1. **Гранулярность системы.** Является ли «сайт» и «мобильный бэкенд» одной системой с двумя
   фронтами или двумя системами? От этого зависят и карта, и метрики. Предварительно: одна
   система = один жизненный цикл релиза.
2. **Межсистемные связи `measured`.** Пока они `declared`. Чтобы снять их автоматически,
   нужен сквозной идентификатор — `traceparent` или корреляционный id в шине. Он есть
   далеко не везде; пока честнее рисовать `declared` и не притворяться.
3. **Кто в команде владеет `decisions.yaml`.** Технически это ревью в merge request.
   Организационно — вопрос, на который у каждой команды свой ответ, и он определяет, будет
   ли механизм работать вообще.
4. **Порог `until` по умолчанию.** 180 дней — гипотеза. Проверяется на первом же годовом
   цикле: если к концу срока массово продлевают не глядя, срок надо не увеличивать, а
   привязывать к релизному циклу команды.
