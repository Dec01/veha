# Как поднять Веху в Docker

Образ показывает каталог проекта (корень с `atlas.yaml`) только на просмотр. pytest и
allure-pytest в образе есть — их тянет partest, — но запуска наборов из вебморды нет: в
команде образа нет `--allow-run`, а `veha serve` отказывается сочетать `--allow-run` с
адресом не на loopback (внутри контейнера сервер слушает `0.0.0.0`).

## Сборка и запуск

Из корня репозитория `veha`:

```text
docker build -t veha:local .
docker run --rm --read-only --cap-drop ALL --security-opt no-new-privileges \
    -p 127.0.0.1:8770:8770 -v "/путь/к/проекту:/data:ro" veha:local
```

Или пример compose (корень проекта — переменная `VEHA_PROJECT`):

```text
VEHA_PROJECT=/путь/к/проекту docker compose -f compose.example.yaml up --build
```

**Порт — только на `127.0.0.1` хоста.** `-p 8770:8770` без адреса публикует порт на все
интерфейсы хоста, `--network host` открывает сервер в сеть, а на Linux проброс портов
Docker обходит ufw. Входа во вебморду нет — так не запускать.

**Образ собирается из рабочего дерева,** включая незакоммиченное (контекст — разрешающий
список `.dockerignore`: `pyproject.toml`, `README.md`, `LICENSE`, `veha/`, без `.env*`,
кэшей и временных файлов). Для выпуска собирайте из чистого клона или из `git archive`.

**Сеть.** Сборке нужен индекс пакетов — она ставит зависимости. Работающий сервер никуда
не ходит: ни телеметрии, ни загрузок при старте. Это держит код Вехи, а не образ:
исходящий трафик из контейнера ничем не ограничен — в закрытом контуре закрывайте его
сетью Docker или межсетевым экраном.

## Закрытый контур

Для установки, которую проверяют на firewall заказчика, `Dockerfile` из репозитория —
отправная точка, а не готовый рецепт:

- **закрепите базу по digest** (`FROM python:3.14-slim@sha256:…`) — тег `3.14-slim`
  со временем указывает на другой образ;
- **ставьте зависимости из списка с хэшами**: сначала `pip install --require-hashes -r
  requirements.lock` (все пакеты закреплены и с `--hash`), затем сам пакет
  `pip install --no-deps .`; список собирайте там, где вы ему доверяете, или ставьте из
  своего индекса или wheelhouse;
- держите процесс обновления digest и constraints — без него закрепление устаревает
  вместе с уязвимостями базы.

В репозиторий это не вписано нарочно: digest без процесса обновления хуже тега
(см. [[proposals]]).

## Проверка после запуска

```text
curl -s -o /dev/null -w "%{http_code}\n" -H "Host: localhost:8770" http://127.0.0.1:8770/
curl -s -H "Host: 127.0.0.1:8770" http://127.0.0.1:8770/api/graph | head -c 200
curl -s -o /dev/null -w "%{http_code}\n" -H "Host: evil.example:8770" http://127.0.0.1:8770/api/graph
curl -s -o /dev/null -w "%{http_code}\n" -X POST -H "Host: localhost:8770" http://127.0.0.1:8770/api/runner/clean
```

Ожидается `200`, начало JSON графа, `400` («недопустимый Host» — так выглядит страница с
подменой DNS) и `409` (режим просмотра). В журнале контейнера (`docker logs`) при старте —
предупреждение «слушаю 0.0.0.0:8770 — не только loopback»: внутри контейнера так и должно
быть.

## Что настраивается

| Что | Как |
|---|---|
| Область, если их на диске несколько | `ATLAS_SYSTEM`, `ATLAS_ENV` в окружении контейнера |
| Другой порт хоста (`127.0.0.1:9000:8770`) | `VEHA_ALLOWED_HOSTS=localhost:9000,127.0.0.1:9000` |
| Имя за своим обратным прокси на 443 или 80 | `VEHA_ALLOWED_HOSTS=veha.internal:` — двоеточие без порта |
| Закрытый каталог проекта (Linux, `0700`) | `user: "${UID}:${GID}"` в compose |

`VEHA_ALLOWED_HOSTS` — то же, что повторяемый `--allowed-host` у `veha serve`, через
запятую: `имя:порт` — как есть; `имя` — с портом сервера (8770); `имя:` — заголовок без
порта (браузер не пишет порт, когда он стандартный: 443 для https, 80 для http). Шаблонов
нет. `127.0.0.1:<порт>` и `localhost:<порт>` разрешены всегда.

## Защита изменяющих запросов

Проверка `Origin`/`Referer` отсекает чужую страницу в браузере, но не любого клиента:
curl без этих заголовков с `Host: 127.0.0.1:8770` пройдёт. Поэтому изменяющие маршруты
(запуск, остановка, очистка, перезапуск, отметки) включаются только `--allow-run`, а
`--allow-run` — только на loopback: с `--host` не на loopback сервер не стартует (код 2).
Ключа-обхода нет — до входа по токену (этап 3 дорожной карты).

## Что сервер читает и пишет

**Читает** только внутри корня: пути разделов, чьё содержимое отдаётся по HTTP
(`screens.images_dir`, `screens.manifest`, `live.snapshot_dir`, `live.container_logs_dir`,
`app_map`, `logs`), вне корня, через ссылку (символическую или junction) или сетевые не
открываются — раздел не отдаётся, причина под шапкой и при старте. Иначе в контейнере
`images_dir: ../…` отдавал бы `/proc/self/environ`. Пути отчётов (`reports`) и
`artifacts_dir` — по правилам `atlas.yaml`: абсолютные допустимы, сетевые — нет.

**Пишет** в режиме просмотра — ничего: ни в `/data`, ни в файловую систему контейнера.
Всё, что сервер умеет писать, включается только `--allow-run`, а его в образе нет:

| Запись | Куда | Когда |
|---|---|---|
| история прогонов `runner.history` | `<artifacts_dir>/<система>/<контур>/runs.json` | после прогона набора |
| отметки МР | `<live.snapshot_dir>/mr_checks.json` | отметка в окне «Live» |
| очистка результатов Allure | файлы `<UUID>-…` в `reports.allure` | кнопка очистки |
| результаты перезапуска кейса | `reports.allure` (пишет pytest проекта) | перезапуск кейса |

`veha export-static` пишет только в `--out` — это отдельная команда, не сервер.

## Пути и права

- Пути в `atlas.yaml` — относительные внутри корня: абсолютных путей хоста в контейнере
  нет. `veha init` пишет в `reports` только такие.
- Сервер работает под uid 10001. На Linux файлы проекта должны читаться «прочими»:
  `atlas.yaml` от `veha init` создаётся с правами `0666 & ~umask` (обычно `0644`), каталоги
  должны иметь `o+x`. На Docker Desktop (Windows, macOS) права тома не мешают.
- В примере compose — `read_only`, `cap_drop: ALL`, `no-new-privileges`, `pids_limit: 128`,
  `mem_limit: 1g`.

## Чего здесь нет

Входа во вебморду: до него (этап 3 дорожной карты) порт публикуется только на loopback
хоста. Публикации образа в реестр — образ собирается из исходников. Состояние — в
[[status]].
