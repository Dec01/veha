# Веха — карта тестирования

Сервер, который сводит наблюдения о системе и о прогонах тестов в один граф и показывает
его в браузере: экраны, эндпоинты, шина, таблицы — и какие тесты что из этого задели.
Сборка графа, эвристики соединения, сцена, показ расхождений. Управление ими (эталон,
принятие, исключение из оценки) — следующий этап, `docs/architecture.md` §10.

**Статус: alpha (0.5.0)**, что стабильно — в разделе «Статус» ниже. Лицензия — MIT.

## Быстрый старт

```text
pipx install veha        # или pip install veha в отдельном окружении — см. «Установка»
veha demo
```

Откроется `http://127.0.0.1:8770` — карта вымышленной системы: интернет-магазин, склад,
биллинг и CRM, 177 эндпоинтов, 605 тестов последнего прогона. Набор приезжает внутри
пакета; сервер над ним только показывает — прогоны не запускаются, на диск ничего не
пишется. Сеть не нужна. Ключи `demo`: `--port` (по умолчанию 8770), `--no-browser`.

Что смотреть и в каком порядке — [обход демонстрации на 7 шагов](https://github.com/Dec01/veha/blob/v0.5.0/demo/README.md).
Та же карта без сервера — [демо на сайте](https://partest.ru/veha/demo/).

### Свой проект

Корень проекта на pytest + partest (там, где `confpartest.py` и `pytest.ini`) становится
корнем данных Вехи:

```text
veha init --root <проект>        # заготовка atlas.yaml; существующий не трогает
```

`init` читает `confpartest.py` (в корне или в подкаталоге вроде `tests/`) как текст, **не
импортируя его** — код проекта не выполняется; находит в настройках pytest (`pytest.ini`,
`pyproject.toml`, `tox.ini`, `setup.cfg`) пути `coverage.json` (`PARTEST_COVERAGE_JSON`) и
`--alluredir`, пишет набор `full` для тренда и шаблоны остальных разделов, а в конце
печатает следующие шаги командами — по порядку:

1. в окружение проекта: `pip install "partest-atlas>=0.4"` (с `[postgres]`, если в
   зависимостях есть драйвер PostgreSQL) и `allure-pytest`, если его там нет;
2. переменные `ATLAS_SYSTEM` и `ATLAS_ENV` — строками для bash, cmd и PowerShell;
3. база (если в проекте есть её признаки) — раскомментировать раздел `database` в
   `atlas.yaml`, строка подключения — в переменной окружения, пользователь только на
   чтение;
4. `partest-atlas collect openapi` и, если есть база, `partest-atlas collect db-schema` —
   контракт и схема базы (команды появляются в partest-atlas 0.3.0);
5. прогон pytest;
6. `veha serve --root <проект>`.

Ключи `init`: `--root` (по умолчанию текущий каталог), `--system`, `--env` — что подставить
в подсказки; по умолчанию, как у остальных команд, `ATLAS_SYSTEM` / `ATLAS_ENV`, а если их
нет — `default` (то, что возьмут `collect` и `serve` без ключей). Код возврата 0 — файл записан, 2 — ничего не записано
(`atlas.yaml` уже есть, нет каталога, негодное имя системы или контура). Раскладка корня —
ниже, «Каталог данных».

## Имена

Решение принято 2026-09-06 и действует везде:

| | Имя | Где встречается |
|---|---|---|
| **Проект** | **Веха** | сайт, интерфейс, документация |
| Имя пакета сервера | `veha` | код этого репозитория |
| Команда сервера | `veha` | `veha serve`, `veha demo`, `veha export-static`; в плане — `veha update`, `veha baseline diff` |
| Агент сбора | `partest-atlas` | PyPI, отдельный открытый пакет |
| Команда агента | `partest-atlas` | `partest-atlas wrap -- …` |
| Технические имена данных | `atlas.yaml`, каталог `atlas/` | конфигурация и артефакты в проекте с тестами |

Технические имена намеренно **не** переименовываются в `veha`: `atlas.yaml` и каталог
`atlas/` — часть контракта с агентом и с уже существующими установками. Имя проекта и
имя формата — разные вещи, и смешивать их дороже, чем объяснить один раз.

Короткое `atlas` как имя команды не используется: оно занято в экосистеме (MongoDB Atlas
CLI), а конфликт имён на чужой машине ловится дорого.

## Семейство

Веха — потребитель открытых пакетов семейства partest; они про неё не знают.

| Часть | Где | Что делает |
|---|---|---|
| [`partest`](https://github.com/Dec01/partest) | [PyPI](https://pypi.org/project/partest/) | харнесс покрытия API и методика; Веха берёт у него маскирование секретов и читает его отчёт `coverage.json` |
| [`partest-atlas`](https://github.com/Dec01/partest-atlas) | [PyPI](https://pypi.org/project/partest-atlas/) | агент сбора: сборщики, адаптеры, обёртка, зонд; владелец формата артефактов |
| [`partest-load`](https://github.com/Dec01/partest-load) | [PyPI](https://pypi.org/project/partest-load/) | нагрузочные профили и метрики деградации |
| **Веха** | этот репозиторий | сведение источников, карта, вебморда, показ расхождений |

Агент записывает наблюдение, сервер делает вывод. Агент ходит в базу, шину и логи
тестируемой системы, поэтому он маленький и читается целиком. Ценность не в сборе, а в
сведении — она здесь.

**Вебморда живёт здесь**, в сервере, и другого места у неё быть не может: она показывает
сведённый граф, находки и эталон — то, чего агент не знает. FastAPI отдаёт и `/api/*`, и
статику; отрисовка — в браузере: карта по слоям на SVG, объёмный вид на Canvas 2D; ни npm,
ни WebGL, ни внешних шрифтов, ни единого внешнего запроса.
Подробности и недостающая аутентификация — [`docs/architecture.md`](https://github.com/Dec01/veha/blob/v0.5.0/docs/architecture.md) §4.6.

## Красные линии

Нарушение любой — дефект, а не компромисс.

1. **Нулевой исходящий трафик.** Ни телеметрии, ни отчётов о падениях, ни CDN, ни внешних
   шрифтов, ни загрузки библиотек из сети. Вебморда открывается на машине без интернета.
2. **Базы только на чтение.** Ни DDL, ни DML. Запрос, не являющийся одиночным `SELECT`,
   отклоняется (`partest.sideeffects.assert_read_only_sql`).
3. **В consumer group не входим.** Смещения читаются, чужие консьюмеры не задеты.
4. **Пишем только в свой каталог.** Артефакты — в `artifacts_dir`, ничего другого в
   тестируемой системе не создаётся и не меняется (о файле отметок МР —
   [docs/wiki/proposals.md](https://github.com/Dec01/veha/blob/v0.5.0/docs/wiki/proposals.md)).
5. **Секреты не показываем.** Всё, что уходит в интерфейс, проходит через `redact`.
6. **Аудит-лог обращений** к базе, шине и логам — в открытом виде, доступен тому, чью
   систему читают.
7. **Догадка подписана как догадка.** Вывод не выдаётся за факт. Сейчас: у требования
   видно, чем установлена связь с тестом — прямой ссылкой из теста или выведена (по
   эндпоинту, по таблице, по названию фичи); связь «эндпоинт — таблица» подписана окном
   теста, в котором снята, а «топик — таблица» — выводом из тишины записей. Единое поле
   `evidence` (`measured`, `inferred`, `declared`) на каждой связи — план, а не то, что
   уже есть ([docs/wiki/proposals.md](https://github.com/Dec01/veha/blob/v0.5.0/docs/wiki/proposals.md)).
8. **В ядре нет домена конкретного проекта.** Всё проектное — в `atlas.yaml`.

## Установка

Нужен Python ≥ 3.14.4. Ставьте Веху в **отдельное окружение**, а не в окружение проекта с
тестами: у сервера свои зависимости (FastAPI, uvicorn, pydantic), и резолвер pip будет
мирить их с пакетами проекта — проигрывает в этом обычно проект. Данные проекта сервер
читает из каталога (`--root`), ставить его рядом с тестами незачем.

```text
pipx install veha                    # команда veha в своём окружении
# или своё окружение:
python -m venv ~/.veha && ~/.veha/bin/pip install veha    # Windows: ~/.veha/Scripts/pip
```

Вместе с пакетом ставится `partest-atlas` (`>=0.4,<0.5`) — владелец формата артефактов;
сервер читает и проверяет артефакты его кодом. Без доступа в интернет пакеты ставятся
из локального индекса или wheelhouse, сеть для работы не нужна.

Из исходников — для разработки и для пересборки демонстрации. Из корня репозитория:

```text
python -m venv .venv
.venv/Scripts/python -m pip install -e ".[dev]"     # Linux/macOS: .venv/bin/python
```

Демонстрационный набор лежит в пакете, в `veha/demo_data/`; пишет его
`demo/generate.py`, и править набор руками бесполезно — следующий запуск генератора
перетрёт правку. Попробовать на нём `--allow-run` — только на копии во временном
каталоге: с этим ключом сервер пишет в каталог данных (история прогонов, отметки МР),
а `veha/demo_data/` — это дерево пакета.

```text
python -c "import shutil, tempfile, veha.demo as d; print(shutil.copytree(d.data_root(), tempfile.mkdtemp() + '/demo'))"
veha serve --root <напечатанный каталог> --allow-run
```

Колесо для выпуска собирается **только из чистого клона** (`git clone`, затем
`python -m build`), не из рабочей копии: в рабочей копии `veha/demo_data/` мог
измениться — от `--allow-run`, от незакоммиченной генерации, — и в колесо уехало бы
не то, что в репозитории.

## Запуск

```text
veha demo                            # демонстрация на вымышленных данных из пакета
veha serve --root <каталог>          # atlas.yaml, atlas/, coverage.json, allure-results/
veha export-static --root <каталог> --out <каталог>   # статический снимок для сайта
veha init --root <каталог проекта>   # заготовка atlas.yaml, код проекта не выполняется
```

### Каталог данных

`--root` — каталог, который сервер читает. Раскладка по умолчанию:

```text
<корень>/
  atlas.yaml                   конфигурация: разделы агента и разделы Вехи
  atlas/<система>/<контур>/    артефакты агента partest-atlas (artifacts_dir)
  coverage.json                отчёт покрытия partest
  allure-results/              результаты Allure
```

`atlas.yaml` сервер читает только в самом корне, вверх по дереву не ходит. Если прогон
проекта кладёт отчёты в другое место, его называет раздел `reports` — копировать их в
корень не нужно:

```yaml
reports:
  coverage: build/coverage.json      # относительно корня (каталога atlas.yaml)
  allure: build/allure-results
```

Путь лучше держать относительным и внутри корня. Абсолютный (`/ci/out/allure-results`,
`C:/ci/allure`) тоже читается, но привязывает `atlas.yaml` к одной машине: файл лежит в
репозитории, и у второго человека или на конвейере путь не существует. То же в Docker:
в контейнер монтируется корень, абсолютных путей хоста внутри нет — поэтому `veha init`
пишет в `reports` только пути внутри корня, а найденный путь вне корня не записывает и
предупреждает.

Ключи необязательны: нет ключа — путь по умолчанию из таблицы выше. Негодное значение (не
строка, пустая строка, каталог вместо файла и наоборот, управляющий символ, сетевой путь
UNC, неизвестный ключ раздела) не подменяется умолчанием: отчёт не читается, причина видна
под шапкой и при старте. Сетевой путь не читается вовсе: на Windows открыть его — значит
обратиться по сети. Если сам `atlas.yaml` не разбирается, сервер поднимается с
умолчаниями — для отчётов так же, как для `artifacts_dir`, — и показывает ошибку файла:
настройки, которую не прочитать, нет, и искать отчёты «где-то ещё» не из чего.

Очистка `allure-results` из окна раннера удаляет только файлы прогона Allure
(`<UUID>-result.json`, `<UUID>-container.json`, `<UUID>-attachment.*`; `executor.json`,
`environment.properties` и `categories.json` остаются) и только если каталог лежит внутри корня; каталог вне корня и ссылка
наружу очищаются средствами проекта. Вложение сервер отдаёт, только если его называет
тест этого каталога и имя — имя вложения Allure: каталог `reports.allure` бывает общим с
проектом, и остальные файлы в нём по имени не отдаются. Ключей командной строки для этих
путей нет: где прогон кладёт отчёты — свойство проекта, и раннер, очистка и
`export-static` видят один и тот же путь.

`export-static` пишет снимок вебморды, которому сервер не нужен: страницу, статику и
ответы API JSON-файлами. Он открывается из любого подкаталога статического сайта под
CSP без `'unsafe-inline'`; действия, которым нужен сервер (перезапуск, раннер, опрос
«Live», отметки МР), в нём выключены с подписью «в демо недоступно». Скрипты и стили
страница грузит с версией по содержимому в адресе (`static/api.js?v=<хеш>`), так что
долгий кеш JS и CSS на хостинге не мешает обновлению; саму страницу и `api/*.json`
хостинг кешировать надолго не должен; при выкладке `static/` кладут раньше `index.html`,
иначе новый адрес может закрепиться в кеше за старым файлом. **Снимок публикует
всё, что видно в вебморде** — контейнеры, логи, merge request'ы, шаги и вложения тестов;
снимок настоящих данных наружу не выкладывают, для витрины есть вымышленный набор
`veha demo` (из исходников — `--root veha/demo_data`).

Ключи `serve`: `--port` (по умолчанию 8770), `--no-browser`, `--system`/`--env` — какую область
показывать (иначе `ATLAS_SYSTEM`/`ATLAS_ENV`, как у агента; имя — один сегмент
`[A-Za-z0-9._-]+`), `--allow-run` — разрешить из вебморды запуск наборов pytest из
`runner.suites`, остановку, очистку, перезапуск кейса и отметки МР (по умолчанию только
просмотр, ничего не пишется). `--host` — адрес IPv4, на котором слушать (по умолчанию
`127.0.0.1`; имя узла не принимается — его пришлось бы разрешать через DNS);
`--allowed-host ИМЯ[:ПОРТ]` (повторяемый) и переменная `VEHA_ALLOWED_HOSTS` (через
запятую) — ещё значения заголовка `Host`, без порта — порт сервера. За своим HTTP/HTTPS
прокси задают `--public-origin http(s)://имя[:порт]` или `VEHA_PUBLIC_ORIGIN`: один точный
origin без userinfo, пути, query и fragment. Стандартный порт 80/443 нормализуется без
явного `:порт`; его `Host` автоматически разрешается. Прокси должен сохранять исходные
`Host`, `Origin` и `Referer`, а не переписывать их.

Аутентификации пока нет, поэтому сервер по умолчанию слушает только `127.0.0.1`, отвечает
только на `Host` `127.0.0.1:<порт>`, `localhost:<порт>` и явно разрешённые
`--allowed-host` (шаблонов нет — иначе вернулся бы DNS rebinding) и отдаёт CSP без внешних
источников. Изменяющие запросы с чужой страницы отсекаются по `Origin`/`Referer`; для Host
публичного origin ожидается его HTTP/HTTPS-схема, для остальных Host поведение прежнее — это
защита от браузера, а не от любого клиента: запрос без этих заголовков (curl, скрипт)
проходит. От прочих клиентов защищает то, что изменяющие маршруты включаются только
`--allow-run`, а `--allow-run` сервер принимает только на loopback: вместе с `--host` не на
loopback он отказывается стартовать (код 2), обхода нет — до входа по токену. Адрес не на
loopback без `--allow-run` (`--host 0.0.0.0` — для контейнера) сервер принимает с
предупреждением: любой, кто дотянется до адреса, увидит граф и логи. Пути из `atlas.yaml`,
чьё содержимое сервер отдаёт (`screens.images_dir`, `screens.manifest`, `live.*`,
`app_map`, `logs`), — только внутри корня и не через ссылки; иначе раздел не отдаётся, а
причина видна под шапкой и при старте. Секреты (авторизация, пароли, токены, куки)
маскируются во всём, что уходит в интерфейс: вложения, логи, разбор падений.

### Окружение и атомарная история Allure в runner

Доверенный `atlas.yaml` может переопределять окружение pytest на уровне всего runner или одного
suite. Значение `null` удаляет унаследованную переменную; настройки suite имеют приоритет над
общими. `ATLAS_SYSTEM` и `ATLAS_ENV` всегда соответствуют выбранной области и не переопределяются.
Значения env не попадают в API, историю или lifecycle-manifest.

```yaml
runner:
  env:
    PROJECT_OPTIN: null       # внешний opt-in не должен незаметно менять набор
  allure: {}                  # opt-in; без этого раздела прежнее поведение не меняется
  suites:
    api:
      args: [tests/api]
      env:
        PROJECT_MODE: api
```

Раздел `runner.allure` подключает `veha.allure_store` к runner. Отсутствующий или YAML-null
раздел выключен, `{}` включает умолчания: `store: .veha/allure`, `keep: 2`,
`command: [allure, generate]`, `timeout: 300`. Команда — argv без shell; runner добавляет
`raw, -o, report, --clean`. Raw (`reports.allure`) и store обязаны быть обычными непересекающимися
каталогами строго внутри корня; ссылки и junction отклоняются до pytest.

Перед прогоном runner повторяет незавершённую ротацию и удаляет из raw только стандартные файлы
Allure, сохраняя проектные файлы. Затем выполняет pytest с явным `--alluredir`, останавливает его
process group и публикует отчёт. При отсутствии `*-result.json` статус — `no_results`, генератор
не вызывается. Состояние отчёта (`not_run`, `running`, `no_results`, `published`, `failed`,
`rotation_failed`) видно отдельно от исхода тестов в текущем прогоне и истории. Ошибка или timeout
Allure не меняет `returncode` pytest; required `after_run` получает итоговый `report_status` и всё
равно выполняется. При включённом Allure общий OS lock удерживается на весь запуск, публикацию и
required `after_run`, даже если lifecycle-плагины не настроены.

Хранилище оставляет по умолчанию **два снапшота на каждый `system/env/suite`** независимо от
`runner.history_limit`. Оно копирует `history` из предыдущего опубликованного отчёта того же набора,
собирает новый отчёт в `.staging` на той же файловой системе и атомарно переключает относительную
ссылку `latest`:

```text
<root>/<system>/<env>/<suite>/
  runs/<run_id>/index.html   # сгенерированный отчёт и veha-allure.json
  raw/<run_id>/              # копия сырых результатов
  latest -> runs/<run_id>
  state.json                 # опубликованные run_id, от старого к новому
```

Сбой генерации или переключения `latest` оставляет прежний отчёт и историю нетронутыми. Сбой
удаления старого снапшота не откатывает новый: статус `rotation_failed` и его ошибка видны
отдельно, но новый raw считается опубликованным, доступен для просмотра и обновляет карту. Даже
при сбое между переключением `latest` и записью `state.json` этот raw выбирается без перезаписи
`runner.history`; `recover()` перед следующим прогоном повторяет ротацию. Неопубликованные
каталоги `runs` в историю не поднимаются. Старый `latest`, который является обычным каталогом,
автоматически не мигрируется.

Для независимого CI-адаптера остаётся публичный Python API `veha.allure_store.publish()` и
`recover()`: хранилище принимает функцию генерации и само не запускает процессы. Проектный
ingest может вызывать этот API из своего Python-адаптера. Настоящий Allure CLI, ротация
трёх публикаций до двух, POSIX symlink и nginx проверены локально на синтетических данных;
unit/fault-тесты используют генератор-имитацию, а на Windows без права symlink — файловый
адаптер `latest`.

### Накопленная карта и сохранённые прогоны

Структура системы и результаты отдельного запуска — разные представления. После завершённого
прогона с опубликованным Allure (включая `rotation_failed`) Веха обновляет накопленную карту в
`.veha/map/<система>/<контур>/state.json`. Частичный набор добавляет или заменяет наблюдения
своих тестов, не удаляя остальные. Повтор одного параметризованного variant заменяет только его
связи: если в новом прогоне прежняя связь не наблюдалась, она исчезает, а соседние variants и
тесты сохраняются. Полная замена задаётся явно:

```yaml
runner:
  suites:
    api:
      args: [tests/api]
      map_scope: api       # api или ui
      map_full: true       # заменить только эту область карты
    ui:
      args: [tests/ui]
      map_scope: ui
      map_full: true
```

Runner задаёт агенту `ATLAS_RUN_ID`, поэтому из накопительных `db.effects` и `bus.flow` в state
попадают только записи текущего `run.id`, а не вся история файла. Для `ui.flow` используются его
реальные `nodeid/variant/run`: partial удаляет старые связи повторённого variant даже при новом
пустом артефакте, full empty очищает UI-область. Непустой legacy partial без `run` прежнее
состояние сохраняет и показывает проблему; legacy full остаётся совместимым. Полный API-набор не
удаляет UI-область, а полный UI-набор — API. Для `containers.logs` остаются прежние правила:
partial объединяет записи, full заменяет документ. Вложения состояния пересобираются только из
финальных тестов, без накопительного union. Ошибка чтения накопленного состояния видна в
диагностике и не подменяется пустой картой. Удаление старых raw-снимков при ротации Allure
накопленную структуру не стирает. Все родители `state.json` проверяются на symlink/junction до
чтения и создания каталогов; запись за пределы корня не выполняется.

На странице прогона можно выбрать сохранённый снимок из `runner.allure`: в список попадают
только завершённые, полные и опубликованные запуски (`published` или `rotation_failed`), чьи
raw-результаты ещё существуют. Выбор применяется к сводке, списку, карточке теста и вложениям;
клиент передаёт только идентификатор из этого списка, не путь. Attempts одного variant (для
legacy — nodeid/file) сворачиваются по фактическим `start/stop`: в сводке, списке, вызовах и
вложениях остаётся только последняя попытка, а raw-файлы всех попыток сохраняются. Вложение
отдаётся лишь тогда, когда его называет финальный тест выбранного снимка. Ссылочные
`*-result.json` не читаются: проблема видна в API, карточка такого результата возвращает 404.
Поэтому история просмотра ограничена числом сохранённых raw-снимков (`runner.allure.keep`, по
умолчанию два на suite), а накопленная карта этим пределом не ограничена. `export-static`
выгружает один выбранный прогон целиком — его список, карточки и вложения из одного raw-каталога;
переключателя сохранённых прогонов в статическом снимке нет.

В карточке падения traceback показывается в том виде, в каком его записал Allure, с пределом
30 000 символов от начала строки; отдельного выделения фрагмента от `Traceback` до исходной
причины сейчас нет. Шаги и длинные имена переносятся без переполнения карточки. На странице
runner наборы можно искать по имени и фильтровать по области API/UI.

### Lifecycle-плагины

Проект может зарегистрировать свои обработчики `validate`, `after_run` и `recovery` в
`atlas.yaml`. Это код проекта, как и вызываемый Вехой pytest: сервер не знает его домен и не
получает команду из браузера.

```yaml
lifecycle_plugins:
  project_cleanup:
    label: Project cleanup
    kind: command
    command: [python, scripts/cleanup_adapter.py]
    cwd: .
    stages: [validate, after_run, recovery]
    required: true
    timeout: 600
    suites: [full]
    env: [PROJECT_DSN_ENV]
    implementation: adapter-v1
    implementation_files: [src/project/cleanup.py]
    editable: false
    settings:
      mode: {type: string, default: marked}
```

`command` — argv-массив, shell не используется. `python` означает интерпретатор самого сервера;
скрипт и `cwd` обязаны находиться внутри корня без symlink/junction. Плагин получает минимальное
окружение и только переменные из `env`; их значения в событие и manifest не пишутся, а в выводе,
summary и metrics маскируются даже при печати голым значением без подписи `password=…`.
На stdin подаётся один JSON с `contract_version: 1`, `run_id`, `suite`, `stage`, `tests_status`,
`report_status`, `scope`, `settings` и `artifacts`. Последняя непустая строка stdout обязана быть
JSON-объектом `{"status":"passed|failed|skipped", "summary":"…", "metrics":{…}}`. Вывод и
результат ограничиваются и проходят redaction. Ненулевой код, timeout, битый JSON и неуспешный
required-результат видны отдельно от исхода pytest; required `validate` не пропускает запуск.

Страница «Плагины» разрешает менять только enabled у необязательного плагина и scalar-настройки,
объявленные с безопасным `default` (`string`, `integer`, `number`, `boolean`). `editable: false`
делает всю запись read-only. Обязательный плагин нельзя отключить. Изменения атомарно пишутся в
`.veha/lifecycle/state.json`, попадают в `audit.jsonl` и действуют только на будущие прогоны.
Встроенной аутентификации у сервера нет: `actor` в audit обозначает канал `web-ui`, а не имя
пользователя; персональную личность должен давать доверенный auth-слой развёртывания.

До pytest Веха атомарно сохраняет `.veha/lifecycle/runs/<run_id>.json` со snapshot команд, настроек
и SHA-256 реализации. `implementation_files` объявляет дополнительные импортированные файлы:
их пути и байты входят в digest после файла команды; выход за корень и ссылки отклоняются.
Пустой или отсутствующий список не меняет прежний digest и остаётся совместим со старыми
snapshots. Общий OS lock удерживается до конца required `after_run`. После сбоя сервера
следующий запуск сначала выполняет `recovery` из snapshot. Если команда, файл адаптера или
дополнительный файл, `implementation` либо версия контракта изменились, автоматический recovery
и новый прогон блокируются для ручного разбора. Без раздела `lifecycle_plugins` прежнее поведение
и файлы состояния не создаются.

### Docker

`Dockerfile` в корне репозитория собирает образ `veha serve --root /data` из рабочего
дерева (`pip install .`, не с PyPI; незакоммиченное тоже уезжает — для выпуска собирайте из
чистого клона или `git archive`) на `python:3.14.4-slim`. Сервер работает под
непривилегированным пользователем (uid 10001) и без `--allow-run`. pytest и allure-pytest
в образе есть — их тянет partest; запуск наборов из вебморды закрыт не составом образа, а
отсутствием `--allow-run` в команде и отказом `serve` сочетать его с адресом не на
loopback. Сеть нужна только сборке (зависимости); работающий сервер никуда не ходит — это
держит код Вехи, а не образ: исходящий трафик из контейнера ничем не ограничен,
закрывайте его своей сетью.

```text
docker build -t veha:local .
docker run --rm --read-only --cap-drop ALL --security-opt no-new-privileges \
    -p 127.0.0.1:8770:8770 -v "/путь/к/проекту:/data:ro" veha:local
# или пример compose:
VEHA_PROJECT=/путь/к/проекту docker compose -f compose.example.yaml up --build
```

- **Порт — только на `127.0.0.1` хоста.** `-p 8770:8770` без адреса публикует порт на все
  интерфейсы, `--network host` открывает сервер в сеть, а на Linux проброс портов Docker
  обходит ufw — так не запускать. Внутри контейнера сервер слушает `0.0.0.0` (иначе проброс
  до него не дойдёт) и предупреждает об этом при старте. Другой порт хоста
  (`127.0.0.1:9000:8770`) — `VEHA_ALLOWED_HOSTS=localhost:9000,127.0.0.1:9000`, иначе сервер
  ответит «недопустимый Host».
- **Корень — том только на чтение** (`/data:ro`). В режиме просмотра сервер не пишет ничего
  — ни в корень, ни в файловую систему контейнера (`--read-only`).
- **Пути в `atlas.yaml` — относительные внутри корня.** Абсолютных путей хоста в контейнере
  нет; `veha init` пишет в `reports` только такие пути, а пути отдаваемых разделов вне корня
  сервер и не читает.
- **Права.** На Linux файлы проекта должны читаться «прочими» (uid 10001): `atlas.yaml`
  от `veha init` — `0666 & ~umask`, обычно `0644`. Закрытый каталог — `user: "${UID}:${GID}"`
  в compose.

Подробно, с проверкой после запуска, — [docs/wiki/howto/docker.md](https://github.com/Dec01/veha/blob/v0.5.0/docs/wiki/howto/docker.md).

Что сервер прочитал, а что нет и почему, печатается при старте и видно под шапкой вебморды; для
диагностики то же отдаёт `GET /api/artifacts` — это внутренний HTTP-интерфейс вебморды,
его форма может меняться в любой версии. Проверки — `python -m pytest` (без сети и без стенда).

## Статус

Alpha: сервер — устанавливаемый пакет и потребитель `partest-atlas`; подключение своего
проекта начинается с заготовки `veha init`, подключение к базе и сбор контракта —
пока руками (команды `collect` — в partest-atlas 0.3.0).

**Что стабильно.** Версии — [Semantic Versioning](https://semver.org/) с поправкой на
линию `0.x`: пока она не кончилась, ломающее изменение поднимает **минорную** цифру и
записывается в журнале изменений разделом «Сломано». Таблица — в начале
[CHANGELOG.md](https://github.com/Dec01/veha/blob/v0.5.0/CHANGELOG.md).

- **Публичное** — то, на что можно опираться: команды `veha serve`, `veha demo`,
  `veha export-static`, `veha init` и их ключи; порт по умолчанию 8770; переменные `ATLAS_SYSTEM` и
  `ATLAS_ENV`; раскладка каталога данных (`atlas.yaml`, `atlas/<система>/<контур>/`,
  `coverage.json`, `allure-results/`; другие пути — раздел `reports`) и разделы
  `atlas.yaml`, которые читает сервер; история прогонов `runner.history`, отметки
  `live/mr_checks.json`, состояние `.veha/lifecycle/`; функции `veha.allure_store.publish()` и
  `recover()`, их `StoreResult` и раскладка выбранного хранилища `.veha/allure`.
  Публичным контрактом артефактов остаётся формат Atlas.
- **Внутреннее** — меняется в любой версии без записи в «Сломано»: импорт `veha.*`
  (кроме `veha.__version__` и явно названного выше `veha.allure_store`), HTTP-интерфейс `/api/*`,
  раскладка статического снимка и `.veha/map/<система>/<контур>/state.json`. Последний файл —
  записываемое сервером производное состояние, а не стабильная схема для внешних писателей или
  читателей. Подробно, с тем, чего нет, и с ближайшими шагами, —
  [docs/wiki/status.md](https://github.com/Dec01/veha/blob/v0.5.0/docs/wiki/status.md).
Проектное направление дальше — этапы в [`docs/architecture.md`](https://github.com/Dec01/veha/blob/v0.5.0/docs/architecture.md) §10.
