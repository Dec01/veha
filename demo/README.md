# Демонстрация «Вехи»

Просмотрщик карты тестирования: карта по слоям «экран → эндпоинт → шина →
хранилище», покрытие по методике, прогон, требования, контракт.

> **Все данные набора вымышлены.** Ландшафт «Сеть N» (интернет-магазин,
> склад, биллинг, CRM), экраны, эндпоинты, таблицы, топики, контейнеры,
> требования, тесты и прогоны придуманы и построены генератором. Скриншоты
> экранов — нарисованные заглушки.

## Запуск

Набор поставляется внутри пакета `veha`:

```
pip install veha
veha demo
```

Откроется `http://127.0.0.1:8770`. Порт меняется `--port`, браузер не
открывать — `--no-browser`. Сервер над набором поднимается только в режиме
просмотра и читает его на месте, в каталоге установки; записывать ему нечего.

Из исходников — то же самое после `pip install -e .` в корне репозитория.
Набор лежит в `veha/demo_data/`, поэтому `veha serve --root veha/demo_data`
показывает его же (с `--allow-run` — с кнопками запуска, см. ниже).

Сеть не нужна: ни сервер, ни страница наружу не ходят — ни шрифтов, ни
библиотек, ни телеметрии.

Статический снимок того же набора — для сайта, без сервера (из корня
репозитория):

```
veha export-static --root veha/demo_data --out <каталог>
```

В снимке всё для просмотра, «Live» — тоже, на момент снимка. Запуск прогонов,
перезапуск кейса, опрос стенда, лог контейнера и отметки МР выключены с подписью
«в демо недоступно».

> **Снимок публикует всё, что показывает вебморда:** контейнеры и их состояние, логи,
> merge request'ы, шаги и вложения тестов, схему базы. Маскирование секретов —
> эвристика. Снимок настоящих данных наружу не выкладывайте: для витрины есть этот
> вымышленный набор.

## Что показывать: обход на 7 шагов

1. **Карта по слоям.** Открывается раздел «Карта», вид «Слои»: слева направо по ходу
   запроса — экраны, API по доменам (Витрина, Заказы, Склад, Биллинг, CRM, Платформа),
   шина и сервисы, хранилища. Эндпоинт — квадрат: зелёный — покрыт по методике,
   янтарный — частично, пустой — тестов нет; красная рамка — упал в прогоне. Над
   картой те же четыре состояния пилюлями с числами: «упало 35» оставляет яркими только
   упавшие. Справа — сводка: среднее покрытие 66.05%, 566 из 605 тестов зелёные.

2. **Цепочка от кнопки до таблицы.** Нажмите на экран «Заказы»: под ним раскроются его
   элементы, и от каждого протянется связь к эндпоинту, который он вызывает. Нажмите на
   `POST /api/v1/carts` (подпись — при наведении): путь от кнопки «Новый заказ» до таблиц
   `cart`, `order_header`, `payment` и топиков шины; остальная карта гаснет. Сплошная
   линия — снято на прогоне, штрих — объявлено в карте, точки — выведено: запись в
   таблицу приписана по окну теста и могла быть записью фикстуры. В карточке
   справа — тот же путь списком и кнопка «путь целиком».

3. **«Покрытие → Обзор».** Числа прогона, где болит и чего не хватает чаще всего
   (`RequestPermissions`, `RequestCrossField`). Клик по строке «чего не хватает»
   открывает «Эндпоинты» с этим фильтром — и та же подсветка остаётся на карте.

4. **«Покрытие → Методика».** Матрица «эндпоинт × тип проверки». Видно, что дыры не
   равномерны: `Orders`, `Payments`, `Products` закрыты полностью, а `Refunds`,
   `Notifications`, `Audit` — почти пустые. Это и есть то, ради чего инструмент нужен.

5. **«Требования».** Требования из трёх спецификаций, привязанные к узлам карты: прямой
   ссылкой из теста, по эндпоинту, по таблице. Рядом — расхождение: путь
   `/api/v1/customers/{id}/erase` описан в документе, но в реализации его нет. В
   подразделе «Контракт» — обратная сторона: объявлено в OpenAPI, но за прогон не
   вызывалось, и коды ответов, которых контракт не объявляет.

6. **«Система».** Все связи списком, по виду: вызовы экранов, записи и чтения таблиц,
   публикации в шину, упоминания в логах контейнеров; рядом — набор сходства (общие пробелы
   или общий тест), которого на карте нет. Откуда взялась связь — снята, объявлена или
   выведена, — видно на карте и в карточке узла. Схема БД — 52 таблицы, 369 колонок,
   60 внешних ключей; строка таблицы ведёт на карту.

7. **«Прогон».** Разбор последнего прогона: длительность, самые медленные, дерево шагов и
   вложения упавшего теста. В подразделе «Live» — состояние контейнеров стенда (один
   упал, один перезапускается — половина падений объясняется этим) и очередь проверки
   merge request'ов.

Полезные мелочи: `/` — поиск по узлам, `Ctrl+K` — палитра команд, `1` и `2` — виды
карты «Слои» и «Объём» (та же система изометрической сценой), `Esc` — снять выделение.

## Что внутри

Здесь, в `demo/`, — генератор и это описание. Сам набор генератор пишет в
пакет, в `veha/demo_data/`: оттуда его поднимает `veha demo`, и оттуда он
попадает в колесо. Второй копии нет.

```
demo/generate.py        генератор всего набора данных (в колесо не входит)

veha/demo_data/:
atlas.yaml              проектное знание: контейнеры, домены, экраны, live
app_map.yaml            ручная карта интеграций UI ↔ API ↔ шина ↔ хранилище
atlas/default/default/  артефакты агента partest-atlas, схема 2: контракт,
                        схема БД, связи UI, эффекты в БД, события шины, логи,
                        требования, история прогонов
live/                   для вкладки «Live» (не артефакты агента):
                        containers.json, mrs.json — снимки адаптера,
                        mr_checks.json — отметки проверки, их пишет сервер
coverage.json           покрытие по методике partest
allure-results/         результаты прогона (605 тестов, 39 падений)
screens/                манифест экранов и PNG-заглушки
logs/                   лог прогона и логи контейнеров
```

Сервер читает только каталог набора. Артефакты проверяются кодом агента: то же
самое руками — `partest-atlas check veha/demo_data/atlas/default/default`.

Область артефактов — `default/default`: набор описывает один проект. Если в
`atlas/` окажется несколько областей, сервер возьмёт `default/default` и
перечислит остальные в `/api/artifacts`; другую показывают ключами
`--system` и `--env`.

## Пересобрать набор

```
python demo/generate.py
```

Генератор детерминирован: один и тот же набор при каждом запуске, на любом
интерпретаторе и любой ОС (текст пишется с LF и на Windows). PNG с теми же пикселями не перезаписываются — байты сжатия
зависят от сборки zlib, и иначе каждый запуск на другом Python пачкал бы git.
Записи агента — в настоящей форме: экраны `#/…/42`, а не `/#/…/{id}`, у одной
записи эффектов БД nodeid с параметрами `[…]`.
Правки руками в `veha/demo_data/atlas.yaml`, `veha/demo_data/app_map.yaml`,
`veha/demo_data/atlas/` и `veha/demo_data/live/` перетрутся — менять нужно модель
в начале `demo/generate.py`. Генератору нужен установленный
`partest-atlas` не ниже 0.2.1: заголовки артефактов проверяются его `validate`,
контракт, схема БД, связи UI, требования и логи контейнеров собираются его же
функциями, а срезы покрытия в истории прогонов снимает код сервера
(`veha.runner.snapshot_of`) поверх его `collect.history.coverage_snapshot` —
до 0.2.1 тот не переносил `exception`, `scored` и `depth`, и генератор на нём
не запускается. `coverage.json` набора — в форме partest 2.7.0: правило среднего
`meta.avgRule: 2`, `summary.exception`, `scored`, `depth` и глубина у строк.

## Ограничения демонстрационной сборки

* **Прогон не запускается.** Кнопки «Запустить набор», «Перегнать кейс» и
  «Очистить отчёты» отвечают честной ошибкой: в наборе нет ни тестов, ни
  стенда. Показывается история прогонов из артефакта `runner.history`.
  В ней два полных прогона: ночной с opt-in-набором `slow`, включённым
  переменной `RUN_SLOW`, и последний — с тем же набором снятым (14 тестов,
  `meta.selection.optin` в `coverage.json`). Тренд показывает их отдельными
  сериями: состав тестов у них разный.
  Запуск — и отметки МР во вкладке «Live» — разрешает ключ
  `veha serve --allow-run`. У `veha demo` такого ключа нет: с ним сервер пишет
  в каталог данных, а `veha/demo_data/` — дерево пакета. Пробовать — на копии
  во временном каталоге:

  ```
  python -c "import shutil, tempfile, veha.demo as d; print(shutil.copytree(d.data_root(), tempfile.mkdtemp() + '/demo'))"
  veha serve --root <напечатанный каталог> --allow-run
  ```
* **Live-режим читает снимки, а не стенд.** Состояние контейнеров —
  `veha/demo_data/live/containers.json`, логи — файлы из
  `veha/demo_data/logs/containers/`, merge request'ы —
  `veha/demo_data/live/mrs.json`, отметки — `veha/demo_data/live/mr_checks.json`
  (пути — раздел `live` в `atlas.yaml` набора).
  Наружу не ходим.
* **Элементы без `data-testid`.** Агент не записывает видимый текст такого
  элемента, поэтому на экране они сведены в один узел «элемент без
  data-testid»: 17 элементов — 11 узлов, по одному на экран.

## Проверки

`python -m pytest` из корня репозитория: цифры сцены этого набора, сходимость
артефактов с контрактом агента, ответы API, защита вебморды, маскирование
секретов, отсутствие исходящих запросов и закрытых имён. Ни сети, ни стенда не
нужно.
